# CAM 作业面交互设计

> 状态：目标设计（2026-08-30）；本文是交互与产品形态，不替代 [CAM 加工场景设计](cam-machining-design.md) 的工具/闸门/proxy 契约  
> 范围：离线 CAM **编程交付**的作业面——人如何过目、指向、签字、处理例外、交班；以及场景包如何向同一套壳注册自己的阶段、对象与处理逻辑  
> 核心约束：**壳没有固定四阶段**。阶段数量、名称、顺序/分支、主对象、主动作与闸门都由当前场景包提供；壳只提供阶段运行时和共性交互  
> 第一张桌子：接单铣削**新件 / 首件**（棱体/壳体类）。本文 §5.2、§7 的「来件 / 工艺 / 执行 / 交付」是该场景的完整实例，不是壳的固定流程；返修变更、模具开档注册各自阶段，不另起一套作业面  
> 非目标：报价、机床日排产板、刀管/MES 本体、机床边对话式编程、仿真级碰撞与 Z-map 残料（后二者可作为场景包日后的侧视，不进壳）

相关文档：[cam-machining-design.md](cam-machining-design.md)（执行层与四工具）、[cam-capability-market-design.md](cam-capability-market-design.md)（能力类型与安装授权）、[memory-design.md](memory-design.md)（经验审核）。

线框原型（只含界面，不含说明；当前画的是场景 A「铣削新件」，不是壳的固定阶段）：[cam-job-interaction-wireframes.html](cam-job-interaction-wireframes.html)。

## 1. 定位

作业面的工作物与行业一致：来件、工序、刀、刀路、装夹与坐标系、设定单、NC；返修场景还会有父单、变更项和影响表，模具场景还会有分型、电极、策略树与残料。交互壳不预设这些领域对象，只提供 Agent 产品共通的过目、指向、签字、冻结、例外和交班能力；具体对象与阶段由场景包注册。

这覆盖中小离散件、接单铣削、用 NX 等做离线编程的厂，不是「CAM 行业的标准界面」。量产调旧程序、机床边对话、模具五轴、工艺已在 PLM 锁死——工作物还在，主对象和进场路径要换场景包，见 §8。

产品表述：

> 先做新件编程交付，作业面按「一单活」做；换场景时阶段和主对象一起换，壳不换。

编程主界面是**一单活**。工控机排队只在件头和会话列表用一句话出现，不做成机床日排产板。

## 2. 原则

1. **作业对象是正文，对话是页边批注。** 主界面是这一单活；判断、反问和自然语言修改在判断栏，但始终指向场景对象。铣削新件的正文是零件与工序，返修是父单与变更，模具是电极、策略与残料。
2. **能看见的不问，不能猜的一次问清，用车间话。** 材料、行程、刀库、后处理名以档案和读件为准；来料、装夹未定、图纸含糊处必须问。
3. **选择立刻看见后果。** 攻丝、换刀、改余量带来的缺刀、工时、报废风险挂在当前对象上。
4. **人只做判断，机器只做确定的事。** 问人、查本厂经验、拍板在作业面；读件、绑机床、算刀路、对账、打包走带闸门的路径。机床参数不经模型转手。
5. **失败是一等公民。** 空刀路、缺 NC、刀不在库、代理拒绝：钉在当前场景的责任对象上，最多三个动作。
6. **一分钟内先给能用的对象。** 读件简报或工序草案，而不是过程散文。
7. **Agent 有级，级是厂里定的。** 生手厂普通序也过目；熟手厂套路件自动跑，只升级高风险、首件、失败。
8. **操作工过关，这单才算过关。** NC、设定单、对刀点找得到。
9. **经验只能预填，不能代替本单确认。** 高风险必须书面声明；闸门认本单档案，不认聊天记忆。
10. **同一时刻只有一个主对象。** 侧视可以开；壳只认「当前指向对象」，不预设它是工序。铣削新件靠当前序互跳，返修可指向变更项，模具可指向电极或策略节点。

## 3. 角色

| 角色 | 在作业面上 | 第一版 |
|---|---|---|
| 编程员 / 工艺员 | 主用户：过目、指向、签字、处置失败 | 按一人签设计 |
| 工艺主管 | 审经验草稿；将来只看高风险/失败/首件队列 | 记忆库审核即可 |
| 操作工 | 不进作业面；接设定单、NC、只读交付页 | 导出/打印 + 文件 |
| 实施 / 工艺工程师 | 机床档案、场景包、经验采纳 | 不在作业面里教模型说话 |

问答（「这活 CV-850 能干吗」）不绑定场景、也不出现作业阶段，见 §7.11。

## 4. 整屏结构

进了一单 CAM 活之后，人面对的是作业面。会话列表、记忆库、设置仍在产品栏。

```
┌─ 产品栏（会话 / 记忆库 / 设置）─────────────────────────────────┐
│  ┌─ 件头：作业摘要 · 当前阶段 · 注意项 · 阶段主按钮 ──────────┐ │
│  │ 阶段甲│           舞台（一个主对象）              │ 判断栏  │ │
│  │ 阶段乙│                                           │ Agent  │ │
│  │ 阶段丙│     当前场景、当前阶段该看的对象           │ 问齐卡 │ │
│  │  …   │     当前指向对象可带动侧视                 │ 例外  │ │
│  │      │                                           │ 输入  │ │
│  └──────┴───────────────────────────────────────────┴────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

**件头（不滚走）。** 壳固定放作业身份、场景、当前阶段、注意项和唯一主按钮；件号、机床、材料、来料等摘要字段由场景包贡献。主按钮的名称、可用条件和点击语义属于当前阶段（如「按此方案开跑」「签字交付」「确认变更范围」），壳统一承接 busy、防重复、approval 与审计。排队中写清「排在第 2，前面大约还要 X 分钟」。

**动态阶段导航。** 场景包给出阶段描述与状态，壳按本单已冻结的场景版本渲染。阶段可以增删、跳过、回退或形成受控分支，不要求映射到「来件 / 工艺 / 执行 / 交付」。人可以回看已到达阶段，但不能靠乱点跳过场景闸门；任一阶段有待确认、失败或未决时，对应节点亮点。导航是落盘状态的投影，不是几个插件自报的 Tab。

**舞台。** 只放当前阶段的主对象。预览（刀路、设定单、报告）在舞台或侧视打开，不另开页面。场景包决定主对象的类型和视图，壳只负责装载、返回与深链接。

**判断栏（约 320–400px）= 本单的 Agent 对话信息流。** 不是批注框，也不是另开的聊天主舞台：Agent 回合、人的回复、问齐说明、失败处置都在这里按时间往下走。输入框上方钉住当前指向对象，如「改 · 第 4 序 攻 M6」「确认 · 变更项 C-03」「调整 · 电极 E12」；场景包解释这句话可作用的对象与范围。去掉钉子只表示没有局部指向，**不等于默认修改整单**；涉及多对象或整单的变更先给影响预览再应用。结构化问齐项仍摊在当前阶段舞台上，对话里只解释和确认。

空态：还没读件时，舞台就是拖 `.prt` / 图纸的落点。连接未配、机床档案空、NX 不在，用件头灯和判断栏一句人话说明。

窄屏：判断栏可叠成抽屉，舞台不能窄到破坏当前场景主对象；场景 A 以一张完整工序单为最低宽度。不做手机上机编程。

## 5. 动态阶段与主对象

### 5.1 壳的阶段协议

场景包向壳注册一张阶段图，而不是往四个固定页面里填内容。每个阶段至少给出：

- 稳定 `stage_id` 与人话标题；
- 主对象视图，以及该阶段允许指向的对象类型；
- 由本单落盘数据推导出的状态：`locked / ready / active / waiting / blocked / complete / stale / skipped`；
- 当前阻断项、注意项和唯一主动作；
- 可到达的下一阶段、允许回退的位置，以及哪些变化会让本阶段或下游变成 `stale`；
- 产出的领域档案与交付物类型。

业务推进仍由场景服务、确定性工具和闸门完成，客户端描述只负责把真实状态投影成界面，不能仅靠前端点击把阶段标成完成。本单写死 `scenario` 与场景版本；运行中不热换场景图。

### 5.2 场景 A：铣削新件的阶段实例

在第一张桌子里，工序单、刀路、设定单按四个阶段轮流当主对象；点中的那一序带动其余。下面这四项属于 `milling-new` 场景包，不属于壳：

| 阶段 | 主对象 | 人在干什么 | 侧视 / 检视 |
|---|---|---|---|
| 来件 | 读件简报 | 认图、勾声明、定毛坯/装夹/坐标系 | 相似件一条，点开才对比 |
| 工艺 | 工序单 | 过目、拖序、改一刀、开跑签字 | 当前序刀路；刀号/转进/刀库/声明 |
| 执行 | 过程时间线 | 看哪一序在算、处理失败 | 已完成序可看刀路 |
| 交付 | 设定单 + NC 包 | 给操作工的东西、交付签字 | 按序刀路；工序单只读并盖终态 |

设定单是工艺 + 机床快照 + 声明的渲染：工艺阶段是活草稿，交付阶段升主对象。

### 5.3 场景 A：刀路查看与播放

现有 `camind-ui-toolpath-viewer`（轨道球、时间轴播放、HUD、源码抽屉）仍用，挂在本单舞台里，**不跳到对话区「预览」标签**。

两级，都对着场景 A 的当前序：

| 级 | 在哪 | 看什么 |
|---|---|---|
| 侧视 | 工艺 / 执行已完成序 / 交付 NC 旁的小窗 | 当前序轨迹轮廓，确认「有没有、像不像」 |
| 展开播放 | 点侧视或「查看刀路」，**舞台主对象临时换成查看器** | 播放 / 暂停 / 进度、XYZ 与行号 HUD、快移与切削图层、俯视/等轴、点段打开源码 |

判断栏、件头、阶段导航不动。关掉播放（「回工序单 / 回时间线 / 回设定单」）主对象回到该阶段原来的桌子。没有 NC 的序（草稿、空刀路）侧视写明还没有刀路，不能假装在播。

### 5.4 场景 A：来件简报与装夹事实

来件简报在读件完成后应尽快出现。问齐一次出齐、推荐置顶、来料必选。材料、公差、螺纹凡图纸和档案已有的，不再让人复述。

毛坯、装夹、工件坐标系是来件与工艺之间的作业对象，不是工序单脚注。没有下列事实不开跑：

- 来料：锯切 / 已铣六面 / 半成品（哪几面已加工）
- 装夹：虎钳 / 工装 / 未定（未定可以排工艺，不能开跑）
- 坐标系：跟机床档案默认，或本单另定

第一版可以是简报上的卡片，不必上 3D 装夹仿真。

## 6. 当前指向对象

舞台上永远至多有一个「当前指向对象」（可为空）。壳只保存稳定的对象引用与显示标签，不解释其领域含义；场景包负责解析、校验和渲染。引用至少包含 `scenario / stage_id / subject_type / subject_id`，不得只靠列表下标。

指向可以来自舞台点击、侧视反查、判断栏中的结构化对象链接，也可以由失败自动建议；新提醒不能在用户查看别处时强制抢走当前指向，只亮灯并提供「查看」。输入框必须始终显示作用域。没有当前指向时，整句话先按整单意图理解；凡会修改多个对象、让已完成阶段失效或扩大影响范围的动作，都先展示变更预览并由人确认，不能静默落盘。

### 6.1 场景 A：当前序

铣削新件把「工序」注册为主要可指向对象，这是「改一刀」的落点：

- 点工序单第 4 行 → 第 4 序成为当前
- 刀路点到一段 → 回到那一序，有 NC 行则对上
- 设定单点到某一刀/某一序 → 回到该序
- 判断栏里未去钉的话，默认作用在当前序
- 没有当前序时，「换机床」可识别为整单属性；「全部精铣留余量」先列出受影响工序再应用

多选只用于「这三序都删 / 都改余量」。默认单选。拖序是工序单上的手势。

每序可见状态：草稿 / 已冻结 / 在算 / ok / 空刀路 / 失败。另留挂钩（第一版可空）：**本单算的 / 从上一版引用的**，以及件头可挂**父单 / 上一版**。返修和模具场景不继承「当前序」语义，它们分别注册变更项、电极、策略节点等对象。

## 7. 场景 A 的作业生命周期

本节把「铣削新件」场景写到可实现的完整程度，用来验证动态阶段壳；除 §7.1 的进场与路由外，阶段名、当前序、签字对象、失败动作和交付内容都由场景 A 提供，不是其他场景必须照搬的全局流程。

```
进场 ── 来件 ── 工艺 ── 开跑 ── 执行 ── 交付 ── 交班 ── 回写
```

一会话一单活。第二件新开一单。

### 7.1 进场

新会话还不是一单活，**没有**来件 / 工艺 / 执行 / 交付，也**没有件头**（侧栏已标明新会话）。页上只有：品牌、落点、示例、输入。默认就是编程交付。报价 / 顾问以后另开会话。线框见 [cam-job-interaction-wireframes.html](cam-job-interaction-wireframes.html) 左侧「新会话」。

| 动作 | 行为 |
|---|---|
| 拖 `.prt`（+ 图纸）或点「出程序」示例 | 本会话变成一单活，进入来件（新件包） |
| 打开历史单 / 「孔改成 M8」 | 进返修单（变更包） |
| 只问不做 | 仍停在新会话，对话在输入上方展开，不绑定场景、不出现作业阶段 |
| 一句话看不清要干什么 | **仍在新会话**，出一张「这一单要做什么」确认卡（新零件出程序 / 改已有程序 / 先问一下）。不问「场景包」 |
| 未就绪 | 落点旁一句人话（连接/机床），不进作业面排障 |

### 7.1.1 来件路由：哪一个场景包

人不选「场景包」。v1 也**不靠切换 Agent 模式**来选包：新会话默认就是编程交付，件头没有模式下拉。

判断发生在编程交付会话**内部**，由该模式的 skill 看第一下行为和那句话（规则为主；看不清再问）。场景一旦写进本单，壳就加载该包注册的阶段图；首个冻结/签字点之后不再换包。冻结前识别错了可以回到进场重新绑定，已产生的领域草稿按原包作废留痕；冻结后要换场景则从本单克隆为新单。没装的包选不到，直接说未安装。

| 认得准 | 绑的包 |
|---|---|
| 拖新 `.prt` / 「出程序交付」 | A 铣削新件 |
| 「打开上月那单」「孔改成 M8」 | B 返修 |
| 模具开档 / 电极（包已装时） | C 模具 |
| 「能干吗 / 有哪些刀」 | **不绑包**，只问答 |

认不准（「这个也做一下」）→ 仍在新会话，出「这一单要做什么」：新零件出程序 / 改已有程序 / 先问一下。问的是要干什么，不是包名。

能认得就不问；认不得才问。不静默猜。报价、顾问不是本页路由目标。

### 7.2 来件：换件、冲突、问齐

来件阶段可以换 `.prt`、补图纸。一换件，读件重做，未签字的工序草案作废；声明能对上的保留。工艺已签字或执行已开始：换件 = 新开一单，本单只读。
图纸与 3D 打架时，简报并排两条，人勾「以图纸为准 / 以 3D 为准 / 我另说」。系统不静默选边。

问齐卡允许「这几项我不确定」——不确定的项不能当声明，高风险不能靠这一条过闸。开跑前改已勾项，简报和草案跟随。

「跟历史件很像」挂在简报上一条。采纳 = 预填声明和工序套路，仍过本单问齐。拒绝 = 收起。返修场景里「打开父单」才是主路径，与这条不是同一交互。

### 7.3 改一刀与冻结

工艺草稿里，工序单提供一步撤销（拖序、改刀、删序）。开跑之后的反悔走下表，不是无限撤销栈。

| 活的状态 | 改一序 |
|---|---|
| 工艺草稿（未开跑） | 当场改表；受影响行重算缺刀、攻丝进给等 |
| 已签字未跑 / 刚开跑还在准备 | 解冻回草稿，说明「方案变了，要重新签字」；旧 run 作废或标 superseded |
| 已有序跑完 | 不能改已 ok 的序冒充同一 run。两条路：只补后面的序（续跑）；或开「新方案」（已完成序可引用，变更序重算）。件头写清走的是哪条 |
| 交付已签 | 本单只读；要改 = 新开一单（可从本单克隆） |

### 7.4 声明与签字

**声明**勾在问齐卡和工序行上，落入本单档案。闸门认档案。

**开跑签字**看着工序单 + 缺刀灯 + 高风险行。按钮在件头。拒签留在工艺，判断栏写原因（可变成改一刀）。超时不签则不跑。

**交付签字**看着设定单 + NC 清单 + 未决项。检查未全过时，件头红字「交付含未决项」。

开跑后要改声明（例如「其实不攻丝」）：按 §7.3 解冻或新方案，新声明写入新档案，旧 run 保留作废原因。

第一版不做主管代签、双人签。

### 7.5 失败

场景 A 的执行阶段主交互是例外协议。时间线上展开同一形态：发生了什么、常见原因、最多三个动作。判断栏建议钉到失败的那一序，但不强制抢走用户正在查看的对象；阶段节点与件头亮灯，点「查看」后舞台和判断栏才一起切过去。

| 失败 | 动作 |
|---|---|
| 空刀路 | 改毛坯 / 改这一序几何 / 跳过本序（跳过必须人认，交付标未决） |
| 刀不在库 | 换成库里的刀 / 本单记下「要装该刀」并停 / 改工艺去掉这序 |
| 连不上 / 超时 | 确认工控机后重试 / 稍后继续 / 停 |
| 代理拒绝（refused） | 按返回原因改入参，不原样再点一次 |
| 缺 NC / 只生成了刀路 | 只补后处理 / 这一序重跑 / 先交付已有的（未决项可见） |

进行中可以停。已 ok 的保留，当前序标中止，件头变为「续跑 / 改方案后重开」。人离开再回来，落在执行阶段、停在失败序。

### 7.6 等待与排队

件头持续显示「第 n 序在算 · 大约还要 X 分钟」。人可以看已完成序的刀路、开另一单；不能改本单已冻结工艺。算完或失败：人在本单则件头和阶段节点亮灯并给「查看」，不强制抢走正在检查的主对象；不在则会话列表亮灯，回来优先提示例外。进度只活在件头和时间线。

工控机同时只跑一件。第二单开跑时件头写清排队，不报内部错误。

### 7.7 交付与交班

交付阶段主对象是包：设定单（第一眼）、NC 清单（本厂命名，可单下、可整包）、按序刀路、未决项（钉在件头和对应序）。

操作工不进入来件 / 工艺 / 判断栏。第一版：导出或打印设定单、DNC 用的程序、必要时只读交付页（设定单 + 刀路 + 对刀点）。

编程员交班动作就是签字交付。之后本单只读。

### 7.8 首件回写

交付之后或执行失败之后，判断栏固定入口：「这单后来怎样」。人说的话钉在对应序上，生成经验草稿，状态为待主管审，不立刻改下一单的 NC。

采纳发生在下一单的来件/工艺（预填）。范本反推（老师傅 `.prt`）走问答或「收入经验」，不伪装成一次编程交付。

### 7.9 对比

| 对比 | 出现时机 | 看什么 |
|---|---|---|
| 跟历史件 | 来件，点「很像」才开 | 声明差、工序套路差 |
| 跟上一稿方案 | 工艺，解冻或新方案时 | 哪几序增删改 |
| 跟上一跑 | 执行 / 交付 | 哪一序状态变了，NC 是否换了 |

第一版至少做「方案差哪几序」。刀路并排后做。

### 7.10 注意力

件头灯 + 动态阶段导航圆点：问齐未完、有失败、交付有未决。场景 A 中人在交付看设定单时执行失败，「执行」必须亮；其他场景由自己的阶段状态把注意项投影到对应节点。

### 7.11 非本单

| 用户意图 | 去向 |
|---|---|
| 编程交付 | 绑定匹配的场景包，显示该包注册的阶段图 |
| 机床 / 能否干 / 有哪些刀 | 问答，不建单 |
| 加工完 NC 在哪 | 已交付则打开交付舞台对应文件；否则判断栏指一次 |
| 要接 MES、要同步刀库 | [产品顾问](cam-capability-market-design.md)，不是本作业面 |

## 8. 场景包

壳（件头、动态阶段导航、当前指向、判断栏、冻结/签字原语、例外容器、交付物框、父单与引用挂钩）三种活共用。场景包注册完整阶段图；阶段数量、标题、主对象、风险词表、执行范围、主按钮与交付内容可以全部不同。

### 8.1 三种活

**A. 接单铣削新件（第一张桌子）。** 阶段图是「来件 → 工艺 → 执行 → 交付」；读件、认攻丝、排粗精钻攻、整单开跑、全套设定单 + NC。§5.2、§7 按此写。可指向对象以工序为主，另含刀、NC 与失败项；件头预留父单挂钩，序预留引用态。

**B. 返修 / 只改孔（第一个扩展包）。** 阶段图可为「找父单 → 确认变更 → 影响分析 → 增量生成 → 变更交付」，不需要伪装成来件/工艺四阶段。先找回单或件号族，再丢新模型或只说变更；主对象依次是父单、变更清单、影响表（保留引用 / 重算 / 新加 / 作废）、受影响序和增量交付包。问齐只问变更里不能猜的，签字对象是变更范围，默认只跑受影响序；交付是变更单 + 新/改过的 NC +「其余同上一版」。经验主路径是打开父单。主要指向对象是变更项，不是普通工序。

**C. 模具开档（独立包，不套壳体工序单）。** 阶段图可为「开档输入 → 分型/电极 → 策略与残料 → 多程序生成 → 开档交付」，并允许从生成受控回退策略阶段。一单宜为「这一开档」（如型腔从开粗到精），电极作子件。主对象是分型、电极清单、禁走、残料来源、策略树与残料接力；风险词表换为薄壁、电极火花位、禁走、长刃球刀是否在库。侧视需要残料状态（第一版可以是「上一节点留下 / 未知」），交付含多程序、刀伸、电极。主要指向对象是电极或策略节点。修模店现场改精加工时，判断栏仍在；「操作工不进桌」在此场景不作为硬规则。报价与电极计价不塞进作业面。

### 8.2 共用与分叉

| 层 | A 铣削新件 | B 返修 | C 模具开档 |
|---|---|---|---|
| 阶段运行时、指向、冻结/签字、例外容器 | 共用 | 共用 | 共用 |
| 阶段图 | 来件→工艺→执行→交付 | 找父单→确认变更→影响分析→增量生成→变更交付 | 开档输入→分型/电极→策略与残料→多程序生成→开档交付 |
| 主对象族 | 简报、工序、刀路、设定单 | 父单、变更项、影响表、受影响序 | 分型、电极、策略树、残料节点 |
| 当前指向 | 工序为主 | 变更项为主 | 电极/策略节点为主 |
| 高风险 | 来料、攻丝、沉窝 | 变更范围、旧底孔 | 薄壁、刀轴、电极 |
| 确定执行 | 整单或续跑 | 只跑受影响 | 多程序、长任务、中途改精加工再续 |
| 交付包 | 全套设定单 | 增量 + 变更单 | 多程序 + 刀伸 + 电极 |

### 8.3 落地顺序

1. A 按本文做满作业面。父单、序引用态先留位。
2. B 验证壳是否真动态：沿用件头容器、当前指向、失败条和签字原语，但注册五个不同阶段，主指向换成变更项；若仍要把它塞进四阶段，说明壳抽象失败。
3. C 在残料（及日后刀轴）成为对象后再做，不把壳体工序单充型腔。

## 9. 插件切分与插拔

场景包用插件做，与 [能力市场](cam-capability-market-design.md) 的类型一致：插件注册阶段图、状态投影、领域视图、闸门/校验器、交付模板与可选增补工具，**一个** AgentPreset「编程交付」领壳，Skill 做 §7.1.1 路由和红线。不是每个场景复制一套 proxy 和工作台，也不是每个包再挂一个 Preset 让人分类。

```
作业面壳（不随场景卸载）
  件头容器 · 动态阶段导航 · 阶段舞台 · 当前指向 · 判断栏
  原语：冻结/解冻 · approval · 例外 · 作废/引用 · 交付物框
  挂钩：父单 · 对象来源 · 版本
  服务：camJob · camPipeline · machineRegistry · uploads · memory · run 目录契约

        │ 场景包注册阶段图与领域实现
        ▼
场景包（可安装、可卸）
  Skill 片段 + 场景描述 + 插件
  （阶段视图 · 对象视图 · 状态推导 · 风险/闸门 · 交付模板 · 可选工具）
```

| 放进场景包 | 留在壳 |
|---|---|
| 阶段 id/标题/次序或分支、主对象与主按钮 | 动态导航、舞台、返回、深链接、busy 与注意力 |
| 可指向对象类型及领域动作 | 当前指向引用、输入钉、影响预览与审计容器 |
| 风险词表、闸门条件、失败动作 | approval/deny 原语、通用失败形态与恢复入口 |
| 执行范围（整单 / 受影响 / 多程序） | submit+poll、互斥、后台任务、续跑基础纪律 |
| 交付模板与领域页 | 打包、完整性校验、下载、发布留痕 |
| 经验如何过滤 | 记忆服务本身 |

不再按四个业务名声明 `cam.job.incoming/process/risk/package`。建议分成「场景注册」与「通用渲染席位」两层：

- Host 侧 `camJobScenario` 注册表：按 `scenario id + version` 提供阶段描述、状态投影、阻断项、允许转移和只读摘要；状态必须由落盘领域数据推导，不能由客户端自报完成。
- Client 侧 keyed `cam.job.stage.view`：key 为 `<scenario>:<stage_id>`，owner props 给作业身份、阶段状态、当前指向与壳动作；场景包渲染主对象。
- Client 侧 keyed `cam.job.subject.view`：按 `subject_type` 提供侧视或详情；没有实现时壳退回 id、标签、状态和来源的通用只读卡。
- `cam.job.issue.action`：场景为标准例外卡增补最多三个领域动作；壳仍负责 ask/deny/busy 与审计。
- 刀路继续走已有 `cam.nc.preview`；交付物继续走壳的通用文件与预览能力。

阶段描述至少包含 `stage_id/title/view_key/subject_types`，以及由 Host 返回的 `status/blockers/notices/primary_action/allowed_transitions`。场景增补工具用自己的名字（如变更比对），不并行复制 proxy 客户端与后台任务基础纪律；是否复用或扩展 `cam_plan/cam_run/cam_deliver` 由壳的执行契约决定，不能要求所有场景硬套同一组 operations 入参。

概念形状如下，具体 TypeScript/Cordis 类型在实现时再钉：

```yaml
scenario: milling-new
scenario_version: 1
initial_stage: incoming
stages:
  - { stage_id: incoming, title: 来件, view_key: milling-new:incoming, subject_types: [part, question] }
  - { stage_id: process, title: 工艺, view_key: milling-new:process, subject_types: [operation, tool] }
transitions:
  - { from: incoming, to: process, gate: incoming_confirmed }
```

依赖只允许：场景包 → 壳的注册接口、席位与作业/run 契约。场景包之间不互引，壳不 import 某个场景的实现。

**作业信封与 run 分层。** 动态阶段从场景绑定时就存在，不能等 `cam_plan` 产生 run 后才有存储。壳需要一个 `camJob` 服务在绑定场景时创建作业信封，持久化 `job_id/session_id/scenario/scenario_version`、阶段快照、阶段事件、当前指向、issues、artifacts、父单/版本关系与场景扩展区；位置可在实现时决定，但不能只活在浏览器 store 或未知 session event 中。`run_id` 是作业下的一次确定执行尝试，继续使用现有 run 目录、断点续跑和四终态。一个作业可以没有 run，也可以引用多个 superseded/current run。

具体工序、变更表、残料层放作业信封的场景扩展区。阶段快照只供卸包后的只读降级，状态推导和闸门仍以场景领域档案为准，不能把快照当新的事实源。

单上写死 `scenario` 与插件版本。`cam_*` 工具应回到 preset / 场景包注册，避免全局模式也能看见（与 cam-machining-design §6.2 原意一致）。

### 9.1 插拔语义

| 时刻 | 行为 |
|---|---|
| 装入 profile，进程重启后 | 编程交付路由可为新单绑定该场景；用户不需要选包名或另换 preset |
| 企业关闭授权 | 新单不能开这个场景 |
| 某一单进行中卸包 | 不允许；该单只读或失败 |
| 卸包后的旧单 | 壳按阶段快照只读打开通用状态、issues 与 artifacts；特化视图和领域动作消失 |

插拔指厂里装不装、新单能不能路由到该场景。不是运行中热拔，也不是把 NX 通道卸掉。铣削新件第一版可继续落在现有 skill / preset；动态阶段注册接口稳定后，再把简报、工序单、攻丝卡剥成 `camind-scenario-milling-new`。返修建议作为第一个独立场景包，用它验证阶段数量、名称与主指向都能真正变化。

一个场景包的组成示例：

```
camind-scenario-rework/     变更清单、影响表、增量交付
skills/cam-rework/          先找父单、只问变更、签变更（由编程交付 skill 路由进来）
```

作业信封由壳规定场景/版本、父单、对象来源、阶段事件、issues 与 artifacts；run 目录继续规定某次确定执行的任务终态和交付物。场景在自己的扩展区保存工序单、变更清单或残料层，不能自创第二套任务、审批和交付基础设施。

## 10. 与现有实现的关系

[cam-machining-design.md](cam-machining-design.md) 的四工具、闸门、runstate、机床档案、经验预填，对应本文的确定执行层，继续有效。

当前 `/s/:id` 以对话区为主舞台、右侧工作台分「输入 / 交付物 / 加工」，是过渡布局。本文把作业面升为主舞台，判断栏收对话；现有「加工」时间线可成为场景 A「执行」阶段的主对象，现有交付物可成为场景 A「交付」阶段的包，但壳本身不写死这两个阶段。预览留在舞台内，不再跳到对话区标签页。

本文不改 proxy 协议，不要求立刻拆分 `camind-tool-cam`。落地顺序见 §8.3；`camJob` 作业信封、动态阶段注册、当前指向、run 引用与 `scenario` 字段是壳和场景包之间的契约，写入实现时再钉类型。

## 11. DeepSeek Harness 可实现性与插件数量

本节结论限定在本仓库固定的 `@deepseek-ai/dsh 0.1.1-rc.2`。按当前 Cordis Host 服务、客户端 Slot、`webServer` 路由、工具闸门与后台任务能力，本文描述的**产品行为可以由插件实现**；但若要求完全复用现成公开接口、主界面按钮天然进入官方工具审批链且无需适配，则不能称为零缺口实现。预计主体能力约 85%–90% 可直接建立在现有机制上，剩余工作集中在作业级动作调度、签字审计和版本兼容。

### 11.1 能力匹配

| 设计能力 | 可实现性 | 实现判断 |
|---|---|---|
| 场景包动态注册不同阶段图 | 高 | Host `camJobScenario` 注册表提供阶段图与状态投影，客户端按 keyed Slot 渲染 |
| 不同场景使用不同主对象 | 高 | `cam.job.stage.view` / `cam.job.subject.view` 由场景包注册，壳不认识工序、变更项或电极 |
| 阶段增删、跳过、回退和受控分支 | 高 | 转移由 Host 根据落盘领域数据校验；导航只是投影，前端不能自行标完成 |
| 作业信封与 run 分层 | 高 | 新增 `camJob` 服务；现有 run 目录、`runstate`、断点续跑和四终态继续使用 |
| 后台执行、互斥、取消和续跑 | 已具备基础 | 复用现有 `ctx.jobs`、NX 整程互斥、submit+poll 与 runstate 纪律 |
| 风险闸门、拒绝和 Agent 工具签字 | 已具备基础 | 模型调用继续走 `tools/pre-execute` 与官方 approval 缝 |
| 件头主按钮直接开跑、交付或确认范围 | 需要适配 | 普通客户端按钮没有稳定公开的“携带 Agent/开放回合上下文执行工具”接口，须由 `camJob` 动作调度器承接 |
| 卸包后打开旧单 | 可实现 | 作业信封保存阶段快照、issues、artifacts；壳只读降级，领域动作消失 |
| 运行中热装卸场景 | 不支持且非目标 | profile 组合在进程启动时生效；安装/卸载后重启，与 §9.1 的插拔语义一致 |
| 插件升级后继续旧版本活单 | 需约束 | 升级包须保留仍有活单的旧 `scenario_version` 解释器，或先完成显式迁移 |

当前 `ui-shell` 已有根级 Chain Slot 和会话详情布局，能够增加作业面接入点；但 `/s/:id` 仍是“对话主区 + 右侧工作台”的过渡结构。落地时应由 `ui-shell` 只声明稳定的 `cam.job.root` 席位和普通会话/作业会话切换，完整作业面由独立 UI 插件注册，不能把场景 A 的四阶段写进 `ui-shell`。

### 11.2 推荐插件切分

采用“**两个稳定基础插件 + 每个场景一个插件**”的模型：

| 插件 | 类型 | 职责 |
|---|---|---|
| `camind-service-cam-job` | 基础 Host 插件 | `camJob` 作业信封、`camJobScenario` 注册表、阶段推导与转移、动作调度、幂等、签字/审计、run 引用和只读降级数据 |
| `camind-ui-cam-job` | 基础 Client/Host UI 插件 | 件头、动态阶段导航、舞台、判断栏、当前指向、影响预览、例外容器、通用只读视图和场景视图席位 |
| `camind-scenario-milling-new` | 场景插件 | 铣削新件阶段图、简报/工序/刀路/设定单视图、风险与失败动作、整单执行和完整交付模板 |
| `camind-scenario-rework` | 场景插件 | 父单、变更项、影响表、受影响序、增量执行和变更交付模板 |
| `camind-scenario-mold-opening` | 场景插件 | 分型、电极、策略树、残料接力、多程序执行和模具开档交付模板 |

因此新增插件数量为：

- 只完成场景 A 的第一版：**3 个**；
- 完成 A + B、用返修验证动态壳：**4 个**；
- 完成 A + B + C：**5 个**。

一个阶段不是一个插件。一个场景插件同时携带其 Host 注册、客户端阶段/对象视图、状态推导、风险校验、交付模板、Skill 片段与可选工具。现有 `camind-tool-cam`、`camind-service-machine`、`camind-tool-upload`、`camind-tool-memory`、`camind-ui-preview`、`camind-ui-toolpath-viewer`、`camind-service-git-repository` 等作为基础能力复用，不计入上述新增数量。

动作调度第一版放进 `camind-service-cam-job`，不另拆第六个插件。只有当冻结/签字原语需要脱离 CAM、供多个行业作业面复用时，才考虑抽成通用 `human-decision` 服务。

### 11.3 主按钮、审批与确定执行

官方工具审批依赖一个正在进行的 Agent 回合：`approval/asked` 与 `approval/decided` 必须在开放回合内成对审计。普通页面按钮若直接调用自定义 Host API，不会天然进入 `tools/pre-execute → approval → tool` 管线；反过来，若按钮先发送自然语言再等待模型决定调用哪个工具，主动作又失去确定性。

因此件头主按钮采用双入口、同一领域执行内核：

```text
人点主按钮 → camJob.dispatchAction → 作业签字/审计 → 场景校验 → 领域执行服务
模型调工具   → tools/pre-execute    → 官方 approval → 同一领域执行服务
```

`camJob.dispatchAction` 至少承担：

- 以 `job_id + action_id + expected_revision` 做幂等和并发检查；
- 重新读取落盘状态，核对当前阶段、blockers、stale 和允许转移，拒绝仅凭客户端状态推进；
- 生成结构化签字请求并把决定、签字对象、理由、操作者和时间写入作业审计；
- 管理 busy、防重复、取消和后台 `job_id`，动作返回后由客户端重新读取状态投影；
- 把 `scenario/scenario_version/job_id/run_id/action_id` 传给领域服务并关联 artifacts/issues；
- 让页面按钮和 Agent 工具共用从 `camind-tool-cam` 抽出的确定性 `plan/run/deliver` 实现，避免两套 CAM 业务逻辑。

作业级签字不是绕过现有工具闸门：Agent 发起的 `cam_run` / `cam_deliver` 仍走官方 approval；作业面按钮走壳定义的确定性动作闸门。两条入口必须拥有同等的 fail-closed、审计和领域校验强度。日后若 dsh 提供稳定的客户端工具调用与回合内审批 API，可以在不改变场景插件契约的前提下，把动作调度器的签字实现换回平台原语。

### 11.4 现有插件改造边界

**`ui-shell` 只做接入，不承载 CAM 领域。** 增加普通会话态/作业态根布局选择和 `cam.job.root` 席位；作业态把官方 Conversation 收进判断栏，并把舞台留给 `camind-ui-cam-job`。场景标题、阶段数量、工序表、变更表、执行时间线和交付包均不得写死在壳内。

**`camind-tool-cam` 保留执行基础设施，抽出领域服务。** proxy 协议、连接、上传回收、submit+poll、runstate、NC 对账和打包继续有效；把 `cam_plan/cam_run/cam_deliver` 内确定性实现抽成服务方法，供工具包装和 `camJob.dispatchAction` 共用。闸门身份逐步从只认 `run_id` 扩为可关联 `job_id + scenario + run_id`，但不要求首期立即拆散 `camind-tool-cam` 包。

推荐先落 `camind-service-cam-job` 与 `camind-ui-cam-job` 的稳定契约，再做满 `milling-new`；随后以 `rework` 的五阶段、变更项主指向和增量交付做架构验收。只有 B 不需要映射或伪装成 A 的四阶段，才能证明这套壳真正由场景包驱动。
